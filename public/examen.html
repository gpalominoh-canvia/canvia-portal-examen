Contexto

Canvia Market va a salir a producción y el equipo de desarrollo entregó la API de catálogo y pedidos. Eres el QA del equipo: debes construir la suite de regresión de la API con REST Assured + Cucumber (Java 17), dejarla corriendo en la CI y reportar los defectos que encuentres. La API tiene defectos reales: tu trabajo no es que todo pase, sino que tus pruebas demuestren qué funciona y qué no.

La referencia de la API está en /docs. Esa documentación es el comportamiento esperado: si la API hace algo distinto, es un defecto.

Preparación (5 minutos)

  1. Actualiza develop y crea tu rama feature/examen-<tu-nombre> (minúsculas, sin tildes, por ejemplo feature/examen-rosa-quispe).
  2. Levanta el portal en tu PC: docker compose up -d en el repo del portal, o node server.js. Comprueba http://localhost:3000/api/salud.
  3. La URL base se pasa con -DbaseUrl=http://localhost:3000; nunca la escribas en un .feature.
  4. Puedes restaurar los datos con POST /api/reset (por ejemplo, en un hook @Before), pero cada escenario debe crear los datos que necesita.

Tareas

  1. Autenticación mínimo 3 escenarios

    Inicio de sesión correcto con ana (código 200 y token no vacío). Con un Esquema del escenario: clave incorrecta (401), usuario bloqueado (423) y petición sin clave (400). Valida el código y el mensaje del campo error.

  2. Consulta del catálogo mínimo 2 escenarios

    • Buscar por texto (por ejemplo teclado): la lista no está vacía y todos los nombres contienen el texto.
    • Filtrar por categoría: todos los productos devueltos son de esa categoría.
    • Consultar un producto que no existe responde 404.

  3. CRUD de productos mínimo 4 escenarios

    • Crear un producto (201) y comprobar que al consultarlo por su id devuelve los mismos datos.
    • Modificar un producto con PATCH o PUT y comprobar el cambio con una consulta posterior.
    • Eliminar un producto (204) y comprobar que después ya no existe (404) ni aparece en el listado.
    • Intentar crear un producto sin token responde 401.

  4. Validaciones de producto Esquema con 4 filas o más

    Crear un producto con datos inválidos responde 400 con un mensaje claro: sin nombre, precio 0, precio negativo, categoría inexistente, stock negativo.

  5. Pedidos mínimo 4 escenarios

    • Crear un pedido con varios ítems: 201, estado pendiente y total igual a la suma de precio por cantidad.
    • Regla de descuento mayorista (ver reglas de negocio): pedido con un ítem de 5 unidades o más y otro ítem normal.
    • Un ítem con cantidad 0 responde 400.
    • Flujo de estados pendiente → pagado → enviado, y una transición inválida (por ejemplo, de enviado a pagado) responde 400.
    • Un usuario no puede ver el pedido de otro usuario (404). Usa dos usuarios distintos, por ejemplo ana y errores.

  6. Validación de esquema JSON mínimo 2 esquemas

    Valida la respuesta de producto y la de pedido contra un JSON Schema en src/test/resources/schemas/ con matchesJsonSchemaInClasspath (dependencia io.rest-assured:json-schema-validator).

  7. Pipeline y reporte

    El workflow de GitHub Actions levanta el portal con la action oficial, ejecuta la suite excluyendo los escenarios @bug y publica el reporte de Cucumber (artefacto y GitHub Pages). El pipeline debe quedar en verde.

    - name: Levantar Portal Canvia Market id: portal uses: gpalominoh-canvia/canvia-portal-examen@main - name: Ejecutar escenarios run: mvn -B test -DbaseUrl=${{ steps.portal.outputs.url }} "-Dcucumber.filter.tags=not @bug"

  8. Defectos en BUGS.md

    Cada escenario que falla por un defecto de la API se etiqueta @bug (queda fuera de la CI) y se documenta en BUGS.md en la raíz del repo: título, severidad, pasos para reproducir, resultado esperado, resultado obtenido y escenario que lo detecta.

Mínimo para aprobar: 8 escenarios ejecutados que cubran las tareas 1, 3, 5 y 7 (cada fila de un Esquema cuenta; las demás tareas suman puntos), al menos 2 Esquema del escenario, etiquetas @smoke en los escenarios críticos y @regresion en el resto, Gherkin sin URLs ni JSON, y cada escenario independiente de los demás.

Contexto

La tienda web de Canvia Market necesita su suite de regresión de interfaz antes del lanzamiento. Debes automatizar los flujos principales con Playwright + Screenplay + Cucumber (TypeScript), dejarlos corriendo en la CI y reportar los defectos que encuentres. La tienda tiene defectos reales: tus preguntas (Questions) deben verificar el resultado de verdad, no solo que la página cargó.

Comportamiento esperado: los precios se muestran como S/ 1,299.90; el contador del carrito muestra el total de unidades en el carrito; el total del carrito es la suma de precio por cantidad de todos los productos; el nombre y la dirección de entrega son obligatorios.

Preparación (5 minutos)

  1. Actualiza develop y crea tu rama feature/examen-<tu-nombre>.
  2. Levanta el portal (docker compose up -d o node server.js) y abre http://localhost:3000.
  3. La URL base se lee de la variable BASE_URL (por defecto http://localhost:3000); nunca va en un .feature.

Selectores disponibles (data-test)

PáginaSelectores
/ loginusuario, clave, ingresar, error
Cabeceracontador-carrito, cerrar-sesion, ir-al-carrito, ir-a-pedidos, nombre-usuario
/catalogobuscar, categoria, ordenar, producto, nombre-producto, precio-producto, agregar-<id>, resultados, sin-resultados
/carritoitem-carrito, nombre-producto, cantidad, quitar-<id>, total, ir-a-pagar, carrito-vacio
/checkoutnombre, direccion, confirmar, error, pedido-confirmado, numero-pedido
/pedidospedido, numero, total-pedido, estado-pedido, sin-pedidos

Valores de ordenar: nombre-asc, nombre-desc, precio-asc, precio-desc. Los ids de producto van del 1 al 12 (por ejemplo, agregar-4 es el mouse ergonómico).

Tareas

  1. Inicio de sesión mínimo 3 escenarios

    Ingreso correcto con ana (se ve el catálogo). Con un Esquema del escenario: usuario bloqueado y clave incorrecta muestran el mensaje de error esperado. Incluye el usuario lento en un escenario de ingreso correcto: debe pasar sin esperas fijas.

  2. Búsqueda y orden mínimo 2 escenarios

    • Buscar un texto (por ejemplo teclado): todos los productos visibles contienen el texto en su nombre.
    • Ordenar por precio de menor a mayor: los precios visibles quedan en orden ascendente. Convierte el texto S/ 1,299.90 a número en tu Question.

  3. Carrito mínimo 2 escenarios

    • Agregar dos productos distintos: el contador muestra 2, el carrito lista esos dos productos y el total es la suma de sus precios.
    • Quitar un producto del carrito: el contador y el total se actualizan.

  4. Compra mínimo 2 escenarios

    • Compra completa: carrito → pago → pedido confirmado con número; el pedido aparece en Mis pedidos como pendiente.
    • Intentar confirmar sin nombre o sin dirección: se muestra un error y no se confirma el pedido.

  5. Usuario errores opcional, suma en bugs

    Repite tus escenarios de carrito y compra con el usuario errores usando un Esquema del escenario (ana y errores). Si el comportamiento difiere, documenta el defecto.

  6. Screenplay

    Un Actor con la habilidad de navegar la web; tareas de negocio (iniciar sesión, buscar, agregar al carrito, quitar, completar compra), interacciones reutilizables (abrir, escribir, hacer clic, seleccionar) y preguntas (contador, nombres y precios visibles, total, mensaje de error, número de pedido). Los steps solo llaman al actor: sin selectores ni lógica.

  7. Pipeline y reporte

    El workflow levanta el portal con la action oficial, instala Chromium, ejecuta npm run typecheck y los escenarios sin @bug, y publica el reporte (artefacto y GitHub Pages) con las capturas de los fallos.

    - name: Levantar Portal Canvia Market id: portal uses: gpalominoh-canvia/canvia-portal-examen@main - name: Ejecutar escenarios run: npm test -- --tags "not @bug" env: BASE_URL: ${{ steps.portal.outputs.url }}

  8. Defectos en BUGS.md

    Cada escenario que falla por un defecto se etiqueta @bug y se documenta en BUGS.md: título, severidad, usuario, pasos, resultado esperado, resultado obtenido, escenario que lo detecta y captura si la tienes.

Mínimo para aprobar: 6 escenarios ejecutados que cubran login, carrito, compra y pipeline (cada fila de un Esquema cuenta; las demás tareas suman puntos), al menos 1 Esquema del escenario, etiquetas @smoke y @regresion, selectores data-test o por rol, cero waitForTimeout, y npm test y npm run typecheck en verde.
